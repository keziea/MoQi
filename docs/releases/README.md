# 版本发布说明

**一个版本一个文件，文件名与 git tag 完全一致**：`v0.4.1.md` ↔ `v0.4.1`。

## 「修复」和「新增」为什么不拆成两个文件夹

你可能会想：bug 修复和功能更新是不是该各放一个文件夹，分开管理更清楚？

**不建议。** 因为一个版本通常同时包含两类内容 —— v0.4.0 就既加了新功能、又修了两个坑。如果按类型拆开，想回答「v0.4.0 到底改了什么」就得翻两个地方，而且版本号会失去意义：**版本是发布的最小单位，不是变更类型**。

正确做法是**一个版本一个文件，文件内部按类型分节**：

```markdown
## 新增      ← 这一版多了什么能力
## 改进      ← 已有的东西变好了
## 修复      ← 修掉了什么 bug
## 升级说明  ← 用户需要做什么
```

没有内容的节直接省略，不留空标题。这样既保持了版本完整，又能一眼看出这一版的性质。

想找「历史上修过哪些 bug」：看上面索引表的「修复项」列，或者在本文件夹里搜 `## 修复`。

## 三份文档的分工

| 文件 | 面向谁 | 写什么 |
|---|---|---|
| `docs/CHANGELOG.md` | 开发者 / 未来的自己 | 按版本倒序的流水账，偏「改了哪些文件、牵连了什么」 |
| `docs/releases/vX.Y.Z.md` | 使用者 | 这一版对他们意味着什么、要不要做什么 |
| `docs/releases/README.md`（本文件） | 两边都要看 | 版本索引 + 分类规则 |

三处必须对得上：版本号、日期、功能点一致。出现分歧时**以 `releases/` 为准**（那是给用户的承诺）。

## 硬规矩

1. **每发一个版本，必须写一份发布说明** —— 没写不许打包。
2. 文件名必须与 tag 一致：`v0.4.1.md` ↔ `v0.4.1`。
3. 已发布的文件**不再修改**；要更正就发下一个版本。
4. 正文至少要有 `## 新增` / `## 改进` / `## 修复` 其中一节。
5. 打包完成后，把文件名、大小、SHA256 补进「文件校验」。
6. 同一份内容同步到 GitHub 与 Gitee 的 Release 说明，两边一字不差。
7. 新建版本时复制 `_template.md`，别从零写。
